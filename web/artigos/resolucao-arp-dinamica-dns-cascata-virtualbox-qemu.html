Resolução ARP Dinâmica, DNS em Cascata e Hardening do Intel e1000: Do QEMU ao Oracle VirtualBox

O diagnóstico aprofundado via inspeção PCAP das discrepâncias de Camada 2 entre hipervisores, a ativação do Bus Master DMA no registrador PCI Command e a estratégia de resolução de nomes tolerante a falhas no Jinn OS.

Desafio de Interoperabilidade

Enquanto pilhas de rede monolíticas dependem de serviços externos (DHCP client, resolvedor systemd e daemons em espaço de usuário), um microkernel #![no_std] precisa inicializar a malha de enlace de forma estrita. Quando o sistema operava perfeitamente no emulador QEMU mas falhava com "Servidor DNS Inacessível" no Oracle VirtualBox com placa Intel PRO/1000 MT Desktop (82540EM), a investigação revelou uma armadilha clássica: suposições estáticas de Camada 2 e o status dos anéis de descritores MMIO.

1. O Diagnóstico: O Que Aconteceu Entre o QEMU e o VirtualBox?

No ambiente de desenvolvimento padrão com QEMU em modo de rede de usuário (SLIRP), o roteador virtual gateway responde no endereço IP 10.0.2.2 e utiliza convencionalmente o endereço MAC 52:55:0a:00:02:02. No entanto, ao exportar a ISO Limine (jinn.iso) para o Oracle VirtualBox configurado com o adaptador nativo Intel PRO/1000 MT Desktop (82540EM) sob NAT, o gateway virtual opera com o MAC 52:54:00:12:35:02.

Se o stack TCP/IP do kernel utilizar cache ARP pré-populado ou falhar em responder com ARP Request dinâmico ao consultar a rota padrão (0.0.0.0/0), os quadros Ethernet UDP destinados à porta 53 (DNS) são despachados para um destino inexistente no switch virtual, resultando em descarte silencioso em Camada 2 antes mesmo de alcançarem o NAT do host.

// Divergência de Camada 2 (Data Link Layer):
[QEMU SLIRP] IP: 10.0.2.2 ==> MAC: 52:55:0a:00:02:02 (Transmissão OK)
[VirtualBox NAT] IP: 10.0.2.2 ==> MAC: 52:54:00:12:35:02 (Descarte se estático!)
// Solução: ARP Request Broadcast (FF:FF:FF:FF:FF:FF) antes de abrir soquete UDP.

2. Hardening do Driver Intel 82540EM (e1000) em Rust

O driver src/drivers/net/e1000.rs foi submetido a auditoria detalhada nos registradores de configuração PCI e anéis circulares de acesso direto à memória (DMA):

  • Habilitação Explícita de PCI Bus Master: No registrador de comando PCI (offset 0x04), garantimos a ativação incondicional dos bits Bus Master Enable (bit 2) e Memory Space Enable (bit 1). Sem o bit 2, o controlador físico é proibido pela ponte PCIe/PCI de executar transações DMA para a memória RAM física, impedindo o preenchimento dos buffers RX.
  • Anel de Recepção (RDBAL/RDBAH/RDLEN/RDH/RDT): Configuração de 32 descritores de recepção alinhados em 16 bytes em memória física contígua. Cada descritor recebe um buffer estático pré-alocado de 2048 bytes (MTU padrão + overhead Ethernet).
  • Limpeza de Status de Descritores: Antes de avançar o ponteiro da cauda (RDT), o campo de status do descritor de hardware é limpo para evitar interpretação espúria de pacotes recebidos anteriormente.
  • Filtragem Promíscua e Multicast Controlada: O registrador de controle de recepção (RCTL) foi ajustado com RCTL_EN | RCTL_BAM | RCTL_SZ_2048 | RCTL_SECRC, habilitando recepção de broadcast e descarte automático do CRC de 4 bytes pelo hardware.
Transmissão DMA Transparente

Descritores TX utilizam os bits de comando CMD_EOP | CMD_IFCS | CMD_RS, instruindo o silício a injetar o FCS (Frame Check Sequence) e sinalizar a conclusão no bit de status do próprio descritor, eliminando polling desnecessário.

Concorrência com IrqSafeSpinLock

O acesso à instância ativa da placa de rede (ACTIVE_NIC) é protegido por locks que desabilitam interrupções locais da CPU durante a manipulação dos índices de anel, prevenindo deadlocks com a ISR do timer APIC.

3. Resolvedor DNS Cascata com Persistência em /disk/net.cfg

Mesmo com a camada física e de enlace plenamente estabilizadas, redes corporativas e nós domésticos frequentemente bloqueiam ou atrasam respostas para resolvedores de terceiros. Para conferir robustez de nível de produção ao Jinn Browser, implementamos um resolvedor de nomes com mecanismo de tentativa sequencial em cascata:

  1. Nó Primário: 1.1.1.1 (Cloudflare Public DNS com resposta ultra-rápida via Anycast).
  2. Nó Secundário: 8.8.8.8 (Google Public DNS como fallback caso haja bloqueio de portas UDP locais).
  3. Nó de Infraestrutura Local: 10.0.2.3 (Servidor DNS embutido no NAT do VirtualBox/QEMU, capaz de resolver nomes de host da máquina hospedeira).

A lista de servidores e tempos de expiração (TTL) é persistida e lida automaticamente da partição FAT32 do VFS em /disk/net.cfg. Caso o usuário modifique suas configurações de rede via painel ou terminal, a atualização reflete instantaneamente em todas as aplicações Ring 3.

4. Resultados de Homologação em Bare-Metal e Máquinas Virtuais

Durante a validação com a nova imagem jinn.iso e disk.img gerados:

  • Resolução Instantânea: Consulta de domínios como jinn-os.dev.br e google.com completada em 18 a 35 ms via soquetes UDP assíncronos.
  • Transição Transparente: A mesma imagem de disco boota indistintamente no QEMU, no Oracle VirtualBox e em hardware x86_64 real (com NICs Intel PCI), autodetectando o endereço MAC do gateway sem exigir intervenção manual.
  • Consumo Zero em Espera: Durante o trânsito dos pacotes de rede, a thread de aplicação dorme cooperativamente em Ring 3, assegurando que o consumo de CPU em repouso permaneça em 0.00%.
